# MRMAC / QSFP Network Integration (Direct Market Data RX + Order Entry TX)

> Companion to [`01-setup-and-licensing.md`](01-setup-and-licensing.md) and
> [`02-custom-logic-integration.md`](02-custom-logic-integration.md).
> Covers: why MRMAC is required for a direct-network HFT feed handler /
> order-entry path, how to enable it in AVED, and the specific IP
> configuration settings recommended for low-latency operation.

---

## 1. Why MRMAC is required here

The AVED base design (as generated by default) is **PCIe-only** — GT pins for
QSFP are present in the source but intentionally disabled:

> "Since the GTs are not used in this design, the interface ports have been
> commented out." — AVED V80 Source File Overview

> "The AVED base design can be extended to include the MCIO and QSFP for the
> user application by uncommenting the pins from
> `hw/amd_<board>_gen5x8_24.1/src/bd/create_bd_design.tcl` and
> `hw/amd_<board>_gen5x8_24.1/src/constraints/impl.pins.xdc`." — AVED V80
> Hierarchy Overview

For an HFT application that:
- **Receives market data directly from the network** (not via the host), and
- **Sends order entry directly onto the network cable** (not via the host),

...the QSFP path must be enabled, and the hard Ethernet MAC block behind the
QSFP GTs — **MRMAC** (Multirate Ethernet MAC) — must be instantiated and
configured. This is a hard requirement for this use case, not optional.

The V80's QSFP ports use **GTM transceivers**, validated up to 200GbE-class
signaling.

---

## 2. Enabling the QSFP path in AVED

1. Edit `hw/amd_v80_gen5x8_24.1/src/bd/create_bd_design.tcl` — uncomment the
   QSFP-related GT port declarations.
2. Edit `hw/amd_v80_gen5x8_24.1/src/constraints/impl.pins.xdc` — uncomment
   the corresponding QSFP pin constraints (including GT reference clock
   pins).
3. Confirm the GT reference clock frequency actually wired on the V80 board
   for the QSFP quad you intend to use — this must match the **GT RefCLK**
   setting chosen during MRMAC IP customization (see below).

---

## 3. Adding the MRMAC IP

1. In the Vivado IP Integrator canvas (`top.bd`), click **+ (Add IP)** and
   search for **MRMAC**.
2. Double-click the instantiated MRMAC block to open its configuration GUI.
3. After configuring (see settings below), use **Run Block Automation** to
   let Vivado instantiate the matching GTM Quad IP and wire the datapath /
   clock connections (USRCLK, GT REFCLK) automatically. Options offered:
   `Auto`, `Start_with_New_Quad`, `Customized_Connections` — pick
   `Customized_Connections` if you need to target a specific GT quad that
   matches your physical QSFP port.

---

## 4. Recommended configuration settings (HFT / low-latency profile)

| Setting | Recommendation | Why |
|---|---|---|
| **GT Location** | `Include GT subcore in core` | Lets IP Integrator block automation instantiate and wire the GTM quad automatically as part of the MRMAC core, simplifying integration into the existing AVED `top.bd`. |
| **MRMAC Site** | The specific MRMAC/GT quad physically wired to your target QSFP port | Must match the V80 board's QSFP-to-GT-quad mapping; check the board schematic / already-present (commented) constraints in `impl.pins.xdc`. |
| **Port Rate / Preset** | Manually set to your exchange feed's actual rate (commonly **10GE** or **25GE** for direct market-data feeds) — do **not** use a generic "Switching Wide" datacenter preset | The preset shown in AMD's own example (`Switching Wide`) targets general switching use cases, not a fixed low-latency point-to-point feed. Set the exact rate your exchange/venue uses. |
| **AXI4-Stream Clock Mode** | **Low Latency** (not "Independent") | In Low Latency mode the AXI4-Stream clock runs at the same frequency as `tx_core_clk`/`rx_core_clk`, avoiding the extra clock-domain-crossing FIFO that "Independent" mode inserts — directly reduces latency. |
| **Segmented vs Non-Segmented** | Non-Segmented (default at ≤50GE rates) | Segmented mode exists mainly for 100GE Independent-mode configurations; for typical 10G/25G HFT feed rates, non-segmented is standard and simpler to integrate. |
| **GT RefCLK** | Must exactly match the frequency physically wired on the V80 board for the chosen QSFP/GT quad | A mismatch here will prevent link-up entirely; confirm against the (currently commented-out) reference clock constraints in `impl.pins.xdc`. |
| **FEC (Forward Error Correction)** | Disable if the rate/spec and exchange link allow it | FEC encode/decode adds pipeline latency. At 25GE+ FEC may be mandated by the IEEE spec depending on the exact standard in use — check whether your rate/mode requires it before disabling. |
| **IEEE 1588 Timestamping** | Enable | MRMAC supports sub-nanosecond-accuracy hardware timestamping of RX/TX packets — valuable for latency measurement, sequencing, and any regulatory/compliance timestamping requirements in an HFT context. |

## 5. Wiring MRMAC into the design

- **RX path (market data in):** MRMAC RX AXI4-Stream output → your custom
  logic's `s_axis_data` port (see
  [`src/hft_custom_glue_logic.v`](../src/hft_custom_glue_logic.v)).
- **TX path (order entry out):** Your custom logic's `m_axis_data` output →
  MRMAC TX AXI4-Stream input.
- This is a **separate, parallel path** from the QDMA-based bulk host data
  path described in `02-custom-logic-integration.md` — the two are not
  mutually exclusive. A typical HFT pipeline uses the network path for the
  live feed/order entry and the host/QDMA path for control, logging, or
  slower-path order management.
- MRMAC configuration/status/statistics are accessed over its own **AXI4-Lite
  interface** — wire this to the PCIe management crossbar
  (`base_logic/pcie_slr0_mgmt_sc`) the same way as the custom control
  register block, if you need host-side visibility into link status,
  counters, etc.
